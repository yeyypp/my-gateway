# 0. 使用方式

## 0.1 协作模式

- **教学模式（默认）**：Codex 给出结果导向的任务、验收边界并负责审查和排错；用户先思考设计并亲自实现，Codex 默认不预先展开实现方案。
- **共建模式**：用户明确要求直接修改后，Codex 可以实现和验证，同时解释关键设计与取舍。
- **审查模式**：只检查现有实现并给出证据和建议，不主动修改。

模式只决定谁写代码，不降低正确性、测试和安全要求。

### 0.1.1 教学模式的渐进提示

教学模式默认从最低必要提示开始，保留用户发现问题、比较方案和形成实现思路的空间。

1. 首次下发任务时，只说明用户要解决的问题、范围边界、可观察结果、验收标准和整体验证方式；
2. 不主动指定配置格式、文件位置、目录结构、数据类型、函数签名、伪代码、错误文本或逐项测试用例；
3. 用户先给出设计、代码、报错或疑问，Codex 再针对当前信息反馈，不提前回答尚未出现的问题；
4. 提示按“澄清现象 → 提醒约束 → 提供思路 → 给出局部示例 → 参考实现”逐级增加，能够用前一级继续时不直接进入后一级；
5. 用户明确询问最佳实践、要求示例、反复受阻，或当前方向涉及安全、协议兼容性及高返工风险时，可以主动提高提示级别，并说明原因；
6. 验收标准可以具体，实施方案默认保持开放；指出问题时优先解释为什么有问题，不直接替用户重写全部实现。

## 0.2 开始或继续任务

开始新里程碑时：

1. 读取当前进度卡、当前里程碑和直接相关代码；
2. 用只读检查确认仓库真实状态；
3. 简要说明里程碑完成后的可见结果和当前任务在系统中的位置；
4. 按低提示度给出第一个可立即验证的完整工作单元；
5. 根据协作模式由用户或 Codex 实现。

同一里程碑续课时，只说明上次已验证内容、当前工作单元和验证目标，不重复完整导学。核心概念和实现路径在用户提出方案、遇到问题或主动询问时结合实际代码讲解。

除非判断进度所必需，导学前不运行全量测试、Race Detector 或大范围扫描。教学模式下未经授权不修改代码。

## 0.3 学习与实现原则

- 优先形成 `用户操作 → Study Assistant → Gateway → Upstream → 结果 / 日志 / 评价` 的垂直切片；
- 每次推进一个可运行或可验证的完整工作单元；
- 先明确问题、边界和验收，再由用户探索实现；出现具体设计或现象后再解释职责和取舍；
- 不为了架构完整提前创建接口、目录、框架或抽象；
- 生产级差距只讨论与当前增量最相关的 1～3 项；
- 遇到真实错误时优先利用测试、日志和小实验定位；
- 远期阶段只规定结果，进入该阶段时再根据仓库状态拆分任务。

每次学习结束，在回复中给出：

```markdown
- 本次完成：
- 验证证据：
- 我现在能解释：
- 下一步：
```

只有实际产生代码或文档增量、用户要求持久化，或里程碑完成时，才更新本计划。

## 0.4 工作单元粒度

教学过程默认以“完整工作单元”为停顿点，不以单个命令为停顿点。

一个完整工作单元应完成边界清楚的子目标，并产生可观察结果或验证证据。它在任务下发时通常只包含：

1. 本次要实现或验证的行为；
2. 明确不包含的范围和必须遵守的约束；
3. 用户可以观察到的结果；
4. 需要覆盖的测试类别和整体验证方式；
5. 明确的验收与停止条件。

教学模式下，首次下发不把工作单元展开为文件清单、实现顺序或代码骨架。用户开始实现后，已经明确选择且连续、安全、没有决策分支的操作，可以作为同一工作单元的一部分一次性讨论或执行。

`gofmt`、`go mod tidy`、单条测试、构建或创建文件等无分支机械操作，通常只是工作单元中的动作，不能单独作为下一步。

目标一致、连续、安全且没有决策分支的操作应一次性给出。用户可以逐条执行，但 Codex 不应在每条命令成功后暂停并重新规划。

只有以下情况才在工作单元中途暂停：

- 出现与预期不符的结果；
- 后续实现取决于当前输出；
- 存在需要用户选择的设计取舍；
- 操作具有明显风险或需要额外授权；
- 当前现象需要先解释清楚才能继续。

每次给出工作单元时，应同时说明目标、范围、主要操作、验证方法和停止条件。一个工作单元应小于整个里程碑，但大于单个命令或纯机械操作。

# 2. 项目定位与范围

## 2.1 要证明的能力

本项目用于证明以下定位：

> Go 后端与分布式系统工程师，能够构建面向大模型调用的协议层、路由层、治理层和可观测体系，并通过真实应用验证工程取舍。

核心闭环：

```text
用户问题
  → Study Assistant 组织请求
  → Gateway 鉴权、路由和治理
  → 模型服务执行
  → 记录延迟、Token、成本和错误
  → 用户评价
  → 根据证据改进应用或 Gateway
```

AI Gateway 是项目主体；Study Assistant 优先作为参考客户端、真实链路验证入口和后续评价载体，不与成熟聊天产品竞争，也不为了满足计划而制造虚假的使用需求。只有出现真实、重复的学习场景时才扩展其产品能力，不扩展成复杂 Agent 产品。

执行时优先投入 Gateway 的协议、路由、治理、可靠性和可观测能力。Study Assistant 和 Mock 不设独立产品路线：只有在验证 Gateway 行为、支持真实重复使用场景，或构造真实 Provider 难以稳定复现的故障时才修改；能由 `curl`、标准客户端或测试内 `httptest.Server` 完成的验证，不扩展辅助组件功能。

# 3. 目标系统与演进约束

## 3.1 目标系统

```text
CLI / 可选 Web Study Assistant
              │ HTTP / SSE
              ▼
           Go Gateway
 Auth / Router / Rate Limit
 Timeout / Retry / Fallback / Circuit
 Logs / Metrics / Token / Cost
              │
       ┌──────┼──────────┐
       ▼      ▼          ▼
    Mock A  Mock B  Real LLM / Local Model
              │
        可选 MySQL / Redis
```

运行方式按需求演进：本地进程 → Docker Compose → 可选 Kubernetes。

## 3.2 Study Assistant 最小边界

- 读取 GitHub Issue、代码、Diff 或本地文本文件；
- 发起非流式或 SSE 请求；
- 输出模型结果、路由、耗时和错误；
- 逐步保存 Token、成本和人工评价；
- 只知道 Gateway 地址、客户端 Key 和逻辑模型；
- 不知道真实上游地址与 Provider 密钥。

不要求自动修改仓库、完整 Agent、向量数据库或复杂 RAG。

Study Assistant 达到“能发起当前 Gateway 调用、观察结果和触发必要的客户端行为”后即停止扩展；协议兼容、超时、取消、失败和指标的主要实现与证据应落在 Gateway。Mock 只提供确定性验证所需的最小上游行为，优先由局部测试服务器承担；只有手动演示或 Compose 复现需要时才增加常驻 Mock 能力。

## 3.3 架构原则

- 多个真实上游出现后再扩展 Router；
- 长响应需要改善体验时引入 SSE；
- 真实调用方出现后引入 Auth 和调用方配额；
- 可复现上游故障后引入 Retry、Fallback 和熔断；
- 服务数量增加后引入 Compose；
- 多副本出现后再引入 Redis；
- 真实管理需求出现后再做 MySQL、Admin API 和前端。

只有满足以下至少一项时才新增抽象：

- 已有两个真实实现；
- 测试需要替换依赖；
- 当前模块职责已混杂；
- 明确的后续需求能通过抽象降低复杂度。

## 3.4 配置与模型注册的唯一事实来源

Route、Upstream 和模型注册使用同一份领域语义演进：

1. P0 默认由 YAML / JSON 在启动时生成不可变运行快照；
2. 未做数据库时，模型能力、价格和路由规则继续扩展同一份文件结构；
3. 若后续引入数据库，文件只负责首次导入，Admin API 修改数据库并原子替换运行快照；
4. 不允许文件和数据库同时静默覆盖配置，也不建立平行的注册模型；
5. 请求记录保存实际快照标识、逻辑模型、Provider 和路由结果，避免配置变化改写历史语义。

- 检查点 B 通过，可以开始投递。

# 7. 阶段 C：P0 完整作品（W10～W11）

## 7.1 W10：模型服务平台化

目标：在已有调用链上增加兼容性、模型注册、Token、成本和简单可解释路由，不构建复杂规则引擎。

核心范围：

- 审计 `/v1/chat/completions` 非流式、流式和错误行为；
- 形成支持、透传、忽略和拒绝的兼容矩阵；
- 使用一个标准 OpenAI-Compatible 客户端调用自定义 Base URL；
- 扩展现有 Route / Upstream 与真实模型映射，增加版本、能力、价格和状态；
- 从上游 Usage 获取 Token；缺失时记录未知，不伪造精确值；
- 正确处理流式 Usage 最终写入；
- 计算并标明估算成本与上游账单的区别；
- 路由首版只使用能力匹配、健康状态，以及静态优先级或成本中的一种；
- 保存路由选择原因并进行确定性测试。

暂不做：

- 无法验证的机器学习评分；
- 同时组合大量动态权重；
- 没有真实需求的 Responses API、Tools 或多模态；
- 与现有配置并行的第二套模型注册源。

验收：

- 标准客户端和 Study Assistant 均可调用；
- 应用只使用逻辑模型名；
- 修改注册配置可以切换上游；
- Token 存在与缺失、价格变更和流式 Usage 有测试；
- 用户能看见 Provider、模型版本和路由原因；
- 至少比较一次真实任务的效果、延迟和成本；
- 能解释平台层与推理引擎层的边界。

## 7.2 W11：真实使用闭环与求职交付

目标：停止增加基础设施，用代表性任务发现问题、完成一次改进，并整理为可复现作品。

真实任务集：

- 覆盖至少三类任务，例如 Issue 分析、陌生调用链、Diff 审查、测试设计或故障日志；
- 建议完成 10～20 次有意义的使用，不以凑数量为目标；
- 记录任务类型、模型、路由、TTFT、耗时、Token、成本、状态、评价和备注；
- 持续到能够发现至少一个有证据、值得改进的问题。

反馈改进：

1. 记录现象、证据和影响；
2. 选择一个边界清楚的问题；
3. 先补复现测试或实验；
4. 实施最小修改；
5. 再次运行同类任务并比较结果；
6. 说明仍未解决的边界。

求职交付：

- README 第一屏说明用户问题和项目价值；
- 提供架构图、快速启动、演示请求、测试命令和已知限制；
- 展示非流式、流式和 Fallback 的关键数据流；
- 准备一套 5～10 分钟可重复 Demo；
- 编写 100～150 字项目介绍和 3～5 条有证据的简历 Bullet；
- 整理 10～15 个高质量项目面试问题；
- 不使用无法证明的“生产级”“百万 QPS”等表述。

验收：

- 任务记录可从日志、导出文件或可选页面复核；
- 至少一个问题完成前后对比；
- 新读者能按 README 运行核心 Demo；
- 重要结论都能在代码、测试、指标或文档中找到证据；
- 能从用户价值讲到 Gateway、模型平台、失败边界和工程取舍；
- 检查点 C 通过。

# 8. 可选扩展

可选扩展不阻塞 P0，也不提前拆成固定内部增量。只有目标岗位、真实需求或求职反馈提供明确信号时进入。

## 8.1 管理面、MySQL 与 React（原 W8，P1）

适用信号：需要展示 B/S 系统、动态管理路由或持久化历史。

核心结果：

- 应用面、数据面和管理面边界清楚；
- MySQL 保存 Route、Upstream、请求、路由快照和评价；
- Token 和成本支持 unknown / measured / estimated；
- Admin API 校验配置并原子替换运行快照；
- React + TypeScript 提供分析、流式展示、历史和最小管理页面；
- 管理接口独立鉴权，Secret 和原始输入有明确策略。

验收：数据库重启后数据仍在；Migration 可重复；非法配置不污染运行状态；页面能追踪任务到模型和路由。

## 8.2 Kubernetes 与 Redis（原 W9，P1）

适用信号：需要证明多副本部署、共享状态或目标岗位明确要求 Kubernetes。

核心结果：

- 使用 Kind、Minikube 或 K3d 部署 Gateway 和必要依赖；
- Deployment、Service、ConfigMap、Secret、Liveness 和 Readiness 行为明确；
- 用实验展示内存限流在多副本下的偏差；
- 使用 Redis 原子操作实现全局限流；
- Redis 不可用时的 Fail-open / Fail-closed 策略明确；
- HPA 保持 P2，不作为验收条件。

验收：Pod 重建后服务恢复；普通上游失败不触发重启风暴；多个副本共享同一配额；Redis 故障行为可复现。

## 8.3 开源贡献（原 W12，P1）

适用信号：目标岗位重视开源经验，或已经找到范围小、状态明确的 Issue。

推荐路径：

1. 复现一个边界 Bug、协议问题、测试缺口或文档错误；
2. 梳理相关调用链和现有测试；
3. 提供失败证据或兼容性用例；
4. 提交聚焦的补丁并运行项目要求的验证；
5. 条件允许时提交 PR 并响应反馈。

开源 PR 不作为 AI Gateway 作品完成的硬门槛。外部仓库状态或维护者决定不会阻塞 P0。

## 8.4 岗位专项（P2）

- Envoy / Higress：仅在岗位明确要求数据面、控制面或插件经验时进入；
- React 强化：仅在岗位明显偏 B/S 全栈时增加状态管理、测试和 E2E；
- HPA：先有可靠指标、资源请求和多副本需求，再验证扩缩容；
- Responses API、Tools 和多模态：仅由真实应用需求触发。

## 9.2 代码类里程碑完成标准

- 功能或实验已存在于仓库；
- 有端到端演示或可复现验证步骤；
