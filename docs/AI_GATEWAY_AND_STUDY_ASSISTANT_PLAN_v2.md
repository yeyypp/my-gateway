> 用途：本文件既是项目路线图，也是 Codex 的教学与进度判断依据。

## 0. Codex 使用说明

### 0.1 每次开始任务前

Codex 应先完成以下步骤：

1. 阅读本文件；
2. 检查当前仓库结构、`git status`、最近提交和测试结果；
3. 对照“当前进度”与每一天的验收标准，判断真正完成到哪一步；
4. 只处理当前未完成的一天，不提前堆叠后续功能；
5. 判断当天功能是否来自参考应用的真实需求；如果尚无真实需求，说明它属于基础能力、实验验证还是求职展示项；
6. 先说明当天要解决的问题、相关概念、最小实现路径及对应的生产级参照，再辅助用户实现。

### 0.2 教学原则

本项目以用户亲自实现为主。除非用户明确要求直接修改代码，否则 Codex 应优先：

1. 解释当前问题；
2. 指出可选设计及取舍；
3. 给出函数职责、数据流、伪代码或测试思路；
4. 让用户先写；
5. 审查用户实现；
6. 通过错误现象、日志和测试引导用户定位；
7. 最后才给出局部代码建议。

不要一次性生成整天甚至整周的完整实现，不要为了“架构漂亮”提前创建大量接口、目录和抽象。

从第 2 周开始，Codex 还应检查参考应用是否持续通过 Gateway 完成真实任务。新增功能应尽量能回答：它解决了哪个用户问题，如何验证改善，是否有使用数据或故障现象作为依据。

#### 0.2.1 以生产级实践作为教学参照

本项目允许学习阶段的实现保持简单，但教学、设计和代码审查应尽量以生产级代码为目标和参照。这里的“生产级”不是要求用户从第一天起实现所有复杂机制，而是要求 Codex 说明一个功能在真实生产环境中的完整形态、质量要求和风险边界。

每次指导实现或审查代码时，Codex 应明确区分：

1. **当前必须做到**：为了保证正确性、安全性和当天学习目标，当前实现不可省略的内容；
2. **当前允许简化**：为了控制学习范围而暂不实现的内容，以及这样简化的适用边界；
3. **生产级通常还需要**：真实生产环境中需要补充的设计、异常处理、测试、可观测性和运维能力；
4. **演进路径**：从当前实现升级到生产实现的合理时机和步骤。

生产级参照不能只停留在“还要优化”这类笼统描述。应结合当前功能，具体说明以下相关维度：

- 正确性与边界条件；
- 错误语义、失败处理和恢复策略；
- Context、超时、取消以及连接、Body、Goroutine 等资源生命周期；
- 并发安全、容量上限和背压；
- 输入校验、鉴权、敏感信息保护等安全要求；
- 配置管理、默认值、启动校验和动态变更边界；
- 结构化日志、指标、Tracing 和告警；
- 单元测试、集成测试、故障测试、Race Detector 和必要的性能测试；
- Go 惯用写法、命名与注释、错误包装、依赖管理、`gofmt`、`go vet` 和适用的静态检查；
- API 兼容性、代码可读性、包与模块职责和可维护性；
- 部署、灰度、回滚和运行手册等运维要求。

Codex 在给出生产级参照时，应提供与当前任务相称的具体示例，例如关键接口或数据结构、局部代码、测试用例、失败场景或检查清单；不要求一次性给出完整生产系统。

“当前不实现”不等于“不需要了解”。凡是为了学习节奏而省略的生产级能力，应说明省略原因、可能风险和后续补齐位置。反过来，也不要仅以“生产级”为理由提前引入尚无真实需求的框架、中间件或抽象。

### 0.3 进度判断规则

某一天只有在以下条件都满足时才能标记完成：

- 功能已经存在于仓库；
- 有相应测试，或有明确且可复现的手动验证步骤；
- 验收标准全部通过；
- 当天要求的文档已经补充；
- `go test ./...` 通过；
- 涉及并发时，`go test -race ./...` 通过；
- 没有用临时硬编码绕开当天要学习的核心问题。

Codex 不应仅根据“我做完了”直接更新进度，应结合代码和验证结果判断。

### 0.4 修改本文件的规则

每完成一天，Codex 可以协助更新：

- 顶部“当前进度”；
- 对应日期前的复选框；
- “进度日志”。

不要删除原计划。计划需要调整时，应在“计划变更记录”中写明原因。

# 2. 项目定位与最终目标

## 2.1 职业定位

本项目不把用户限定为“AI Gateway 工程师”，而是用于证明以下定位：

> Go 后端与分布式系统工程师，向大模型平台后端、模型服务治理、MaaS / AI PaaS 和 AI 应用基础设施迁移。

AI Gateway 是当前最适合的切入口，因为它能够复用用户已有的 Go、控制面、任务治理、生产排障和分布式系统经验，同时逐步接触模型协议、流式输出、成本治理、推理服务和 AI 应用。

Gateway 本身不是最终产品。最终系统必须包含一个真实应用，使用户能够观察完整链路：

```text
用户问题
  → AI 应用组织请求
  → Gateway 鉴权、路由和治理
  → 模型服务执行
  → 记录延迟、Token、成本和错误
  → 用户评价结果
  → 根据真实反馈修改应用或 Gateway
```

## 2.2 五阶段演进

| 阶段 | 目标 | 本计划对应内容 |
|---|---|---|
| 1. 正确代理 | 正确处理 HTTP、Header、错误、超时、取消和资源生命周期 | 第 1 周 |
| 2. 模型服务治理 | 多模型、多上游、SSE、鉴权、限流、Fallback、Retry、熔断 | 第 2～5 周 |
| 3. 平台化 | 可观测、配置管理、请求历史、前端管理、Docker 和 CI/CD | 第 6～8 周 |
| 4. 推理服务接入 | 真实模型、模型注册、Token、成本、K8s 多副本和分布式状态 | 第 3、9、10 周 |
| 5. 用户闭环 | 参考应用持续使用、人工评价、问题发现、迭代和求职材料 | 贯穿第 2～11 周，重点在第 11 周 |

## 2.3 最终目标

实现一个可用于求职展示、且被真实应用持续使用的 AI 应用基础设施项目，具备以下能力：

1. 使用 Go 实现高并发 HTTP Gateway；
2. 支持多个逻辑模型、多个 Provider 和多个上游；
3. 支持普通响应与 SSE 流式响应；
4. 支持 API Key 鉴权、并发限制和请求限流；
5. 支持超时、有限重试、Fallback、健康检查和简化熔断；
6. 提供结构化日志、Prometheus 指标、Grafana 看板和性能报告；
7. 使用 Docker Compose 一键运行 Gateway、参考应用和依赖；
8. 通过 GitHub Actions 完成测试、静态检查、构建和镜像构建；
9. 提供 Go Admin API、MySQL 持久化以及 React + TypeScript 页面；
10. 部署到 Kubernetes，支持多副本、探针、配置、Secret，并理解共享状态问题；
11. 使用 Redis 实现多实例共享的限流状态；
12. 提供 OpenAI-Compatible API，接入至少一个真实或本地模型服务；
13. 建立最小模型注册表，管理逻辑模型、上游模型、能力、版本和价格；
14. 实现“开源项目与代码学习助手”，用于 Issue 分析、调用链梳理、代码审查和测试设计；
15. 记录参考应用的请求历史、模型、延迟、Token、成本、路由结果和人工评价；
16. 完成至少 20 次真实任务，发现至少 3 个真实问题，并完成至少 1 次用户反馈驱动的改进；
17. 形成完善的架构文档、故障分析、压测结果、用户闭环案例和面试讲解材料；
18. 完成至少一次真实开源贡献尝试，优先争取可合并 PR；
19. 选做 Envoy 或 Higress 集成，理解成熟数据面与自研控制面的边界。

# 5. 项目实施原则

## 5.1 问题驱动

每项技术都必须由一个真实问题引入：

- 多个上游出现后再引入 Router；
- 长响应出现后再引入 SSE；
- 并发增长后再引入限流；
- 多副本部署后再引入 Redis 分布式限流；
- 服务数量增加后再引入 Docker Compose；
- 部署和协作需要稳定流程后再引入 CI/CD；
- 管理配置有实际需求后再加入 MySQL、React 和 TypeScript；
- 运行环境复杂后再进入 Kubernetes。

## 5.2 小步提交

每天至少形成一个可回退的提交。提交信息建议：

```text
feat(proxy): propagate upstream status code
test(proxy): cover unavailable upstream
docs(streaming): explain cancellation flow
```

## 5.3 不提前抽象

只有以下情况才抽象接口：

- 已经存在两个真实实现；
- 测试确实需要替换依赖；
- 当前模块职责已经混杂；
- 后续需求已明确，并且抽象能减少而不是增加复杂度。

## 5.4 每日完成标准

每天结束前完成：

- [ ] 功能或实验达到当天目标
- [ ] 自动化测试或手动验证完成
- [ ] 写下一个当天学到的核心概念
- [ ] 更新进度日志
- [ ] 形成至少一个 Git 提交
- [ ] 明确下一天从哪里开始

## 5.5 真实应用与用户闭环

从第 2 周开始，参考应用必须成为 Gateway 的持续调用方。每一项新增能力都应尽量记录：

1. **用户场景**：用户正在完成什么任务；
2. **问题证据**：日志、错误、等待时间、成本或人工感受；
3. **系统改动**：Gateway 或应用做了什么；
4. **验证方式**：测试、指标、对照实验或再次使用；
5. **结果**：体验、可靠性、成本或可解释性是否改善。

至少保留以下人工评价：

```text
有用 / 部分有用 / 无用
```

不要求第一阶段建立复杂质量评分模型。人工评价的目的，是让项目从“实现功能”转为“解决真实问题”。

# 8. 第 1 周：HTTP 请求生命周期

## 本周目标

从“能转发”提升为“正确理解并处理一次 HTTP 代理请求”。

## [x] 第 1 天：梳理现有请求链路

### 实现目标

- 保持当前固定上游转发功能；
- 明确 Gateway 在一条请求中同时扮演 HTTP Server 和 HTTP Client；
- 画出请求和响应经过的代码位置。

### 具体任务

1. 整理当前代码，让程序能够稳定启动；
2. 确认 Gateway 监听端口和 Mock Server 地址；
3. 找出以下步骤对应的代码：
   - 接收客户端请求；
   - 读取或转发请求体；
   - 构造上游请求；
   - 发送上游请求；
   - 接收上游响应；
   - 写回客户端响应；
4. 创建 `docs/request-flow.md`；
5. 画出 Downstream、Gateway、Upstream 的请求和响应方向；
6. 记录当前实现是否会完整读取请求体和响应体。

### 需要理解

- Downstream 与 Upstream；
- HTTP Server 与 HTTP Client；
- 两段独立 HTTP 连接；
- Handler 的职责；
- 反向代理的基本含义。

### 验收标准

- 能通过一次请求得到正确响应；
- 能不看代码口述完整请求链路；
- `docs/request-flow.md` 不超过两页，但包含完整时序；
- 当前代码中不存在明显重复启动或资源泄漏。

---

## [x] 第 2 天：状态码与基础错误语义

### 实现目标

让 Gateway 正确区分客户端错误、上游业务错误和代理错误。

### 具体任务

1. Mock Server 支持：
   - 正常返回 200；
   - 特殊输入返回 400；
   - 特殊输入返回 500；
2. Gateway 正确传递上游状态码；
3. 非法 JSON 返回 400；
4. 上游无法连接时返回 502；
5. 错误响应使用统一 JSON 结构；
6. 日志记录最终状态码和错误类别。

### 需要理解

- Prometheus、Grafana、pprof 和性能分析；
- Docker、Docker Compose、自动化测试和 CI/CD；
- MySQL、Admin API、React、TypeScript；
- Kubernetes、Probe、Secret、HPA；

- OpenAI-Compatible API、模型注册、Token 与成本治理；
- AI 应用 API、请求历史、人工评价和用户反馈闭环；
