## 1. 项目目标与边界

实现一个 Go AI Gateway，重点展示请求准入、资源隔离、多上游选择、故障治理和可观测性，再加入本地模型辅助选路。项目用于补充 Go / LLM 平台后端与模型服务治理的工程证据。

继续使用 `httputil.ReverseProxy` 承担基础转发。自主设计的重点是：请求能否进入、使用哪个上游、失败后如何处理、资源何时释放，以及如何观察这些决策。

客户端定位为 **Gateway CLI**，用于发送通用模型请求、选择路由和观察结果，不再以学习助手为产品目标。当前 `cmd/study-assistant` 及命令保持可用，名称、目录和交互在实现相关调用能力时一起调整，不为更名单独安排开发阶段。

CLI、curl 和标准 SDK 都是可替换的验证入口；客户端只使用 Gateway 地址、调用凭证和公开的模型 / 上游标识，不管理上游地址或 Provider 密钥。Mock 只提供测试和演示需要的行为，不继续建设独立产品。

## 4. 限流与并发保护

要解决的问题：一个调用方的高频请求或长时间流式连接，不能无限占用 Gateway 和上游资源。

范围：最小 API Key 身份识别与逻辑模型访问边界、单进程按 Key 请求频率限制、按 Key 与进程总并发上限。先实现一种内存限流算法，明确它不提供跨副本全局配额。

完成时能演示：

- 无效身份被拒绝；调用方超出请求频率或并发额度后收到可解释的拒绝，其他调用方仍有可用容量。
- SSE 从进入到结束持续占用并发名额，成功、失败和取消都恰好释放；后续重试不重复占用调用方名额。
- 拒绝发生在调用上游之前，调用凭证不进入日志，也不作为 Provider 凭证透传。

以限流边界、额度恢复和并发资源释放的关键测试验收，不扩展用户管理系统或分布式配额。

## 5. 多上游选择与故障切换

要解决的问题：一个逻辑模型只有一个固定上游时，不能分配负载，也不能在故障时选择备用服务。

范围：同一逻辑模型配置多个合格上游、一种简单分配策略，以及有限重试和 Fallback。正常分配、重试同一上游和切换备用上游分别表达，记录每次尝试的目标与结果。

完成时能演示：

- 正常请求可分配到不同候选；某个上游失败时，符合条件的请求可以切换备用，全部失败时返回明确错误。
- 重试与切换共享最大尝试次数和发送前时间预算；请求取消后不再开始新尝试。
- 根据失败类型和请求可重放性决定是否重试；尚未开始响应不代表上游没有执行或计费。
- 客户端响应开始后不再重试或切换，已输出的流不拼接其他模型结果。

复用既有 SSE 与取消测试，新增选择和尝试预算的关键验证；候选能力、地址和凭证继续由 Gateway 配置管理，不建立第二套注册系统。

## 6. 熔断恢复与明确降级

要解决的问题：持续调用故障上游会浪费资源；主能力不可用时，需要有清楚的服务替代规则。

范围：简化熔断状态机、有限恢复探测，以及一条可演示的能力降级策略。切换同等能力的备用上游属于故障切换；切到能力较低的模型属于降级，二者分别记录。

完成时能演示：

- 上游持续失败后暂时停止接收正常请求，经过有限探测确认恢复后重新接入；并发状态转换可靠。
- 调用方取消、本地限流与鉴权拒绝不被计为 Provider 故障。
- 只有配置与请求语义允许时才使用降级模型，结果可追踪；没有合适替代时明确失败，不伪造成功回复。
- 限流、重试、切换与熔断组合后，尝试次数仍受限，资源仍正确释放。

这一阶段收口后直接进入 Prometheus，不夹入客户端增强或完整性能专项。

## 7. Prometheus 可观测性

要解决的问题：不仅能触发治理行为，还能从运行数据判断它是否生效、失败发生在哪里。

范围：可抓取的 Prometheus 指标与一个最小 Grafana 看板，覆盖请求量、错误、延迟、在途并发、限流拒绝、上游尝试、重试 / 切换 / 降级次数及熔断状态。

同时收口流式观测：流持续时间、取消和中断原因，以及明确测量边界的首块耗时。首字节、首个 SSE 事件和首段有效输出要区分；未观察有效输出时不把指标称为模型 TTFT。

完成时能演示：正常流量、超额拒绝、上游故障和恢复在指标与看板上对应；客户端最终结果与每次上游尝试分别统计；流式统计持续到真实结束。标签不使用 Request ID、原始 API Key 或请求正文，避免无界基数。

暂不要求完整告警平台、OpenTelemetry 或专项性能优化；阶段 5 的路由分析耗时与结果接入这套观测。

## 8. 本地 Ollama 辅助选路

要解决的问题：客户端不明确选择上游时，由 Gateway 根据请求内容选择合适的服务，同时保留调用方直接选择的能力。

目标请求链路：

```text
客户端 → 校验、身份与准入
           ├─ 显式选择上游 → 校验目标与权限 → 使用指定上游
           └─ 自动模式 → 本地 Ollama 分析请求 → 校验建议 → 选择合格上游
        → 上游执行与故障治理 → 响应、日志与指标
```

关键约定：

- **显式选择优先。** 客户端指定 Gateway 对外提供的上游标识时跳过 Ollama 分析；未知、无权限或不支持该请求的目标明确拒绝。严格指定的目标不可用时明确失败，只有调用方明确允许备用 / 降级才可切换。
- **自动模式才分析。** 先支持少量可区分的请求类别，例如代码、通用问答和文本处理，再映射到配置中的候选；不追求一开始就判断任意任务。
- 逻辑模型、显式上游选择和自动模式的含义分开定义，保留现有显式逻辑模型调用行为；新增字段或特殊取值在实现时确定，不把已有请求悄悄改成自动模式。
- Ollama 提供分类或选路建议，Gateway 验证建议并执行最终决策；建议不能增加候选、绕过权限和熔断状态，也不能提供任意目标 URL。
- 分析有独立超时和并发上限，并受客户端取消约束；分析调用直接访问配置好的本地服务，避免递归进入自动路由。明确发给分析器的文本范围并限制输入大小。
- 分析失败、超时或结果无效时，自动模式使用配置的默认合格路由；无合格默认路由时明确失败。分析失败与回答上游失败分别记录。

完成时能演示：显式指定不调用分析器；自动请求可根据类别选择不同上游；分析器不可用时行为确定；日志能解释选择来源、实际目标及切换原因，指标能看到额外分析耗时。

关键策略用可控分析结果做确定性测试；再用一组固定样例和真实 Ollama 验证分类效果，记录错分与延迟。保留静态路由作为对照，不预设模型选路一定更准确或更划算。CLI 此时只补通用请求输入、显式 / 自动选择和必要结果展示，并完成适用的更名。

## 9. 兼容、交付与求职展示

主线功能形成后，集中完成必要交付；运行说明和已有问题案例沿途积累。

- 用一个标准兼容客户端验证非流式与 SSE。请求改写只改变 Gateway 拥有的字段，其余字段保持语义透传或明确拒绝，避免重编码静默丢失。
- 最小 Usage 观察区分缺失、真实零值和非零值；普通与流式、多次尝试和提前取消都能说明已知与未知部分，不声称等于完整计费。
- 提供最小容器 / Compose 启动、CI 和有限等待的优雅退出；停止时在途 SSE 能结束或被取消。
- 提供简短 README、架构图和一套 Demo，展示限流、故障切换、熔断恢复、Prometheus，以及显式 / 自动选路。
- 整理一个真实工程问题的复现、处理和复验记录；需要性能结论时再做受控 Benchmark / pprof，不强行制造优化收益。

完成阶段 1 的可演示能力后即可少量试投，用反馈校准方向；阶段 1～4 加上可复现说明和准确项目材料可作为治理核心版的集中投递依据，自动选路随后补充展示。阶段 5 是已确定的项目主线，但不要求等全部计划完成才开始求职。具体岗位有硬性要求时单独判断，不恢复旧版所有检查点。

Redis 跨副本限流、Kubernetes、管理后台、复杂成本路由、Agent、完整 Trace 和异构 Provider 协议均按实际岗位或使用需求选择，不列入当前串行必做清单。

## 10. 协作与完成方式

默认由用户设计和编码。新工作单元先只读核对当前状态，用一两句话说明为什么现在做、解决什么问题，再给目标、边界、可见结果与关键验收；不提前指定文件、接口、伪代码或逐项实现步骤。遇到具体思路、代码或报错后逐级增加提示，用户明确要求时再直接实现。

每次围绕一个完整行为推进，不把机械命令、测试重构或辅助工具扩展单独变成主线里程碑。测试优先证明自主策略和高风险组合；涉及流式顺序时沿用真实 HTTP 与因果同步，避免用固定等待猜测时序。

完成一个工作单元时审查改动并运行相关测试；涉及共享并发状态时做 Race 检查，阶段收口运行全量 Test、Vet、Build 和差异检查。有失败或新疑点再扩展验证，不重复已足够的证据。

收尾简要说明完成内容、验证证据、仍有的边界和下一步；只有实际进度变化才更新第 2～3 节。详细历史留在 Git、归档或已有笔记中，不持续膨胀主计划。
