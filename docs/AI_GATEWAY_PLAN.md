## 1. 项目目标与边界

实现一个 Go AI Gateway，重点展示请求准入、资源隔离、多上游选择、故障治理和可观测性，再加入本地模型辅助选路。项目用于补充 Go / LLM 平台后端与模型服务治理的工程证据。

继续使用 `httputil.ReverseProxy` 承担基础转发。自主设计的重点是：请求能否进入、使用哪个上游、失败后如何处理、资源何时释放，以及如何观察这些决策。

项目不把自研客户端作为当前建设主线。手工请求、联调和演示默认使用 `curl`，标准 SDK 用于兼容性验证。当前 `cmd/study-assistant` 保留为已有参考客户端，不要求随每项 Gateway 能力同步演进；只有出现明确、重复的客户端使用需求时才做最小调整，不安排更名或独立开发阶段。

无论使用 `curl`、标准 SDK 或已有参考客户端，请求方都只使用 Gateway 地址、调用凭证和公开的模型 / 上游标识，不管理上游地址或 Provider 密钥。Mock 只提供测试和演示需要的行为，不继续建设独立产品。

## 2. 当前状态与下一步

已有基础：

- 最小 Chat Completions 非流式与 SSE 链路；配置化逻辑模型映射、真实模型改写和 Ollama 调用。
- 请求校验、错误响应、Request ID、结构化日志、健康与就绪检查。
- 普通与流式请求的超时已分离；已有首块及时转发、首块后取消、慢客户端背压和上游断流测试。
- 最小 API Key 身份识别与单进程按调用方请求频率限制；无效身份返回 401，超额返回 429，调用方额度相互隔离，拒绝发生在上游调用前。
- 按调用方与进程总量的并发占用控制已接入；普通请求与 SSE 的正常结束、上游失败、客户端取消，以及后续限流 / 参数校验拒绝后的名额恢复已通过测试；同调用方多个在途请求的释放互不影响。
- 一个逻辑模型可配置有序的多个上游；正常请求使用第一个候选，连接前失败且请求仍有效时依次尝试后续候选。每个候选使用自己的默认真实模型与 Provider 凭证；每次上游响应或请求错误及切换决定有日志。
- OpenAI 兼容响应已统一：鉴权、参数、频率 / 并发拒绝及 API 404/405 均返回明确错误；上游 HTTP 错误保留状态并归一化，成功 JSON / SSE 透传。Mock 支持标准 SSE，官方 Go SDK 用于客户端解析与集成验收。

流式与多上游行为测试位于 `cmd/gateway/main_test.go`，完整准入链路的并发生命周期测试位于 `cmd/gateway/concurrency_test.go`，准入与限流测试位于 `internal/middleware` 和 `internal/ratelimit`。

尚未实现熔断、Prometheus 或模型辅助选路。现有 Ollama 是回答请求的上游，还不是路由分析器。

**阶段 1：限流与并发保护已完成；阶段 2：顺序主备切换已按当前范围完成；下一步进入阶段 3：熔断恢复与明确降级。** 首版调用方来自本地环境变量，限流状态只存在于单个 Gateway 进程。阶段 2 的收口边界与验证见第 5 节。

## 4. 限流与并发保护

要解决的问题：一个调用方的高频请求或长时间流式连接，不能无限占用 Gateway 和上游资源。

范围：最小 API Key 身份识别与逻辑模型访问边界、单进程按 Key 请求频率限制、按 Key 与进程总并发上限。先实现一种内存限流算法，明确它不提供跨副本全局配额。

完成时能演示：

- 无效身份被拒绝；调用方超出请求频率或并发额度后收到可解释的拒绝，其他调用方仍有可用容量。
- SSE 从进入到结束持续占用并发名额，成功、失败和取消都恰好释放；主备切换不重复占用调用方名额。
- 拒绝发生在调用上游之前，调用凭证不进入日志，也不作为 Provider 凭证透传。

以限流边界、额度恢复和并发资源释放的关键测试验收，不扩展用户管理系统或分布式配额。

本阶段已按当前范围收口：并发拒绝的可解释错误已补齐，手工演示留到后续演示整理；主备切换期间的名额保持已随阶段 2 验证。

## 5. 多上游选择与故障切换

要解决的问题：一个逻辑模型只有一个固定上游时，连接失败无法选择备用服务。

范围：同一逻辑模型配置有序的多个上游。第一个是主上游；仅当当前候选在获取连接前失败、请求未取消且仍有时间时，才尝试下一个候选。每个候选最多尝试一次，不做正常流量轮换或同一上游重试。

完成时能演示：

- 主上游正常时只调用主上游；连接前失败时按配置顺序切换，全部候选失败时返回明确错误。
- 收到上游响应（包括 HTTP 503）、获取连接后发生错误或响应超时、请求整体超时或客户端取消时不切换；已输出的流不拼接其他模型结果。
- 切换期间只占用一次调用方与进程并发名额，请求结束后释放；每次上游响应或请求错误以及切换决定有简单日志。

已有测试覆盖主上游可用、主上游连接失败后备用成功、全部候选失败、503 / 超时 / 客户端取消不切换，以及切换期间的并发名额占用和释放。候选地址、模型与凭证继续由 Gateway 配置管理，不建立第二套注册系统。

当前以候选数量、请求取消和已有请求超时约束切换，不引入重试与切换共享的尝试预算。SSE 选路与连接阶段的独立发送前时间预算留待后续需要时再做，不能截断已经开始的正常流式响应。

## 6. 熔断恢复与明确降级

要解决的问题：持续调用故障上游会浪费资源；主能力不可用时，需要有清楚的服务替代规则。

范围：简化熔断状态机、有限恢复探测，以及一条可演示的能力降级策略。切换同等能力的备用上游属于故障切换；切到能力较低的模型属于降级，二者分别记录。

完成时能演示：

- 上游持续失败后暂时停止接收正常请求，经过有限探测确认恢复后重新接入；并发状态转换可靠。
- 调用方取消、本地限流与鉴权拒绝不被计为 Provider 故障。
- 只有配置与请求语义允许时才使用降级模型，结果可追踪；没有合适替代时明确失败，不伪造成功回复。
- 限流、切换与熔断组合后，尝试次数仍受限，资源仍正确释放。

这一阶段收口后直接进入 Prometheus，不夹入客户端增强或完整性能专项。

## 7. Prometheus 可观测性

要解决的问题：不仅能触发治理行为，还能从运行数据判断它是否生效、失败发生在哪里。

范围：可抓取的 Prometheus 指标与一个最小 Grafana 看板，覆盖请求量、错误、延迟、在途并发、限流拒绝、上游尝试、切换 / 降级次数及熔断状态。

同时收口流式观测：流持续时间、取消和中断原因，以及明确测量边界的首块耗时。首字节、首个 SSE 事件和首段有效输出要区分；未观察有效输出时不把指标称为模型 TTFT。

完成时能演示：正常流量、超额拒绝、上游故障和恢复在指标与看板上对应；客户端最终结果与每次上游尝试分别统计；流式统计持续到真实结束。标签不使用 Request ID、原始 API Key 或请求正文，避免无界基数。

暂不要求完整告警平台、OpenTelemetry 或专项性能优化；阶段 5 的路由分析耗时与结果接入这套观测。

## 8. 本地 Ollama 辅助选路

要解决的问题：客户端不明确选择上游时，由 Gateway 根据请求内容选择合适的服务，同时保留调用方直接选择的能力。

目标请求链路：

```text
客户端 → 校验、身份与准入
           ├─ 显式选择上游 → 校验目标与权限 → 使用指定上游
           └─ 自动模式 → 本地 Ollama 分析请求 → 校验建议 → 选择合格上游
        → 上游执行与故障治理 → 响应、日志与指标
```

关键约定：

- **显式选择优先。** 客户端指定 Gateway 对外提供的上游标识时跳过 Ollama 分析；未知、无权限或不支持该请求的目标明确拒绝。严格指定的目标不可用时明确失败，只有调用方明确允许备用 / 降级才可切换。
- **自动模式才分析。** 先支持少量可区分的请求类别，例如代码、通用问答和文本处理，再映射到配置中的候选；不追求一开始就判断任意任务。
- 逻辑模型、显式上游选择和自动模式的含义分开定义，保留现有显式逻辑模型调用行为；新增字段或特殊取值在实现时确定，不把已有请求悄悄改成自动模式。
- Ollama 提供分类或选路建议，Gateway 验证建议并执行最终决策；建议不能增加候选、绕过权限和熔断状态，也不能提供任意目标 URL。
- 分析有独立超时和并发上限，并受客户端取消约束；分析调用直接访问配置好的本地服务，避免递归进入自动路由。明确发给分析器的文本范围并限制输入大小。
- 分析失败、超时或结果无效时，自动模式使用配置的默认合格路由；无合格默认路由时明确失败。分析失败与回答上游失败分别记录。

完成时能演示：显式指定不调用分析器；自动请求可根据类别选择不同上游；分析器不可用时行为确定；日志能解释选择来源、实际目标及切换原因，指标能看到额外分析耗时。

关键策略用可控分析结果做确定性测试；再用一组固定样例和真实 Ollama 验证分类效果，记录错分与延迟。保留静态路由作为对照，不预设模型选路一定更准确或更划算。显式 / 自动请求和必要结果展示默认用 `curl` 验证；CLI 增强与更名不作为本阶段验收，只有出现明确、重复的客户端需求时才补最小支持。

## 10. 协作与完成方式

默认由用户设计和编码。新工作单元先只读核对当前状态，用一两句话说明为什么现在做、解决什么问题，再给目标、边界、可见结果与关键验收；不提前指定文件、接口、伪代码或逐项实现步骤。遇到具体思路、代码或报错后逐级增加提示，用户明确要求时再直接实现。

开工前，用户先用几句话说明具体问题、粗方案和预计可观察的结果，允许不完整或有错误。助手先检查假设与边界，保留用户独立推导的空间；卡住时每次只指出一个矛盾、给一个反例或一层提示，等用户继续推导后再增加帮助。用户明确要求时可提供完整解释或直接实现，不要求所有想法都由用户原创，也不限制求助。

每次围绕一个完整行为推进，不把机械命令、测试重构或辅助工具扩展单独变成主线里程碑。测试优先证明自主策略和高风险组合；涉及流式顺序时沿用真实 HTTP 与因果同步，避免用固定等待猜测时序。

手工发送请求、联调和演示时默认提供 `curl` 命令；除非当前工作单元明确验证客户端行为，否则不修改 `cmd/study-assistant`。

完成一个工作单元时审查改动并运行相关测试；涉及共享并发状态时做 Race 检查，阶段收口运行全量 Test、Vet、Build 和差异检查。有失败或新疑点再扩展验证，不重复已足够的证据。

收尾时，先由用户合上代码回答以下问题，助手根据回答核对代码与测试，最后再补充解释，不提前代写总结：

1. 它解决了哪个具体问题？
2. 为什么采用现在的方案？
3. 去掉它，会出现什么可观察的结果？
4. 哪个边界情况最容易写错，如何验证？

分别记录“功能完成”与“理解待补”：实现和验证满足验收时照常确认工程进度；回答不清的地方只选一个具体练习点，不因此重新判定整个功能未完成，也不要求解释完所有细节才能继续。学习反馈指出用户独立提出的方案、发现的边界或修正的预测，不只统计新增功能。

隔几天用一次短复查回看一个旧功能：用户先预测一个场景的结果，再看代码或运行已有测试核对。简短记录“预测、实际结果、差在哪里”，不要求长总结或重讲整个项目。先试几个工作单元，再根据独立预测、解释和修改的表现调整后续范围。

收尾简要说明完成内容、验证证据、仍有的边界和下一步；第 2～3 节只随实际工程进度或近期安排变化更新，理解待补不改写已完成状态。详细历史与短复查记录留在 Git、归档或已有笔记中，不持续膨胀主计划。
