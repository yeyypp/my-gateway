# 0. 使用方式

## 0.1 协作模式

- **教学模式（默认）**：Codex 给出结果导向的任务、验收边界并负责审查和排错；用户先思考设计并亲自实现，Codex 默认不预先展开实现方案。
- **共建模式**：用户明确要求直接修改后，Codex 可以实现和验证，同时解释关键设计与取舍。
- **审查模式**：只检查现有实现并给出证据和建议，不主动修改。

模式只决定谁写代码，不降低正确性、测试和安全要求。

### 0.1.1 教学模式的渐进提示

教学模式默认从最低必要提示开始，保留用户发现问题、比较方案和形成实现思路的空间。

1. 首次下发任务时，先各用一两句话说明为什么现在要做这个工作单元，以及它要解决的具体问题，再说明范围边界、可观察结果、验收标准和整体验证方式；
2. 不主动指定配置格式、文件位置、目录结构、数据类型、函数签名、伪代码、错误文本或逐项测试用例；
3. 用户先给出设计、代码、报错或疑问，Codex 再针对当前信息反馈，不提前回答尚未出现的问题；
4. 提示按“澄清现象 → 提醒约束 → 提供思路 → 给出局部示例 → 参考实现”逐级增加，能够用前一级继续时不直接进入后一级；
5. 用户明确询问最佳实践、要求示例、反复受阻，或当前方向涉及安全、协议兼容性及高返工风险时，可以主动提高提示级别，并说明原因；
6. 验收标准可以具体，实施方案默认保持开放；指出问题时优先解释为什么有问题，不直接替用户重写全部实现。

## 0.2 开始或继续任务

开始新里程碑时：

1. 读取当前进度卡、当前里程碑和直接相关代码；
2. 用只读检查确认仓库真实状态；
3. 简要说明里程碑完成后的可见结果、当前任务在系统中的位置、为什么现在要做它，以及它解决什么具体问题；
4. 按低提示度给出第一个可立即验证的完整工作单元；
5. 根据协作模式由用户或 Codex 实现。

同一里程碑续课时，只说明上次已验证内容、当前工作单元和验证目标，不重复完整导学。核心概念和实现路径在用户提出方案、遇到问题或主动询问时结合实际代码讲解。

除非判断进度所必需，导学前不运行全量测试、Race Detector 或大范围扫描。教学模式下未经授权不修改代码。

## 0.3 学习与实现原则

- 优先形成 `客户端请求 → Gateway → Upstream → 响应 / 日志 / 指标 / 失败边界` 的垂直切片；客户端可以是测试客户端、`curl`、标准 SDK 或 Study Assistant；
- 每次推进一个可运行或可验证的完整工作单元；
- 先明确问题、边界和验收，再由用户探索实现；出现具体设计或现象后再解释职责和取舍；
- 不为了架构完整提前创建接口、目录、框架或抽象；
- 生产级差距只讨论与当前增量最相关的 1～3 项；
- 遇到真实错误时优先利用测试、日志和小实验定位；
- 远期阶段只规定结果，进入该阶段时再根据仓库状态拆分任务。

每次学习结束，在回复中给出：

```markdown
- 本次完成：
- 验证证据：
- 我现在能解释：
- 下一步：
```

只有实际产生代码或文档增量、用户要求持久化，或里程碑完成时，才更新本计划。

## 0.4 工作单元粒度

教学过程默认以“完整工作单元”为停顿点，不以单个命令为停顿点。

一个完整工作单元应完成边界清楚的子目标，并产生可观察结果或验证证据。它在任务下发时通常只包含：

1. 为什么现在要做这个工作单元，以及它与当前里程碑、已有证据或待补缺口的关系；
2. 它要解决的具体问题或规避的实际风险；
3. 本次要实现或验证的行为；
4. 明确不包含的范围和必须遵守的约束；
5. 用户可以观察到的结果；
6. 需要覆盖的测试类别和整体验证方式；
7. 明确的验收与停止条件。

教学模式下，首次下发不把工作单元展开为文件清单、实现顺序或代码骨架。用户开始实现后，已经明确选择且连续、安全、没有决策分支的操作，可以作为同一工作单元的一部分一次性讨论或执行。

`gofmt`、`go mod tidy`、单条测试、构建或创建文件等无分支机械操作，通常只是工作单元中的动作，不能单独作为下一步。

目标一致、连续、安全且没有决策分支的操作应一次性给出。用户可以逐条执行，但 Codex 不应在每条命令成功后暂停并重新规划。

只有以下情况才在工作单元中途暂停：

- 出现与预期不符的结果；
- 后续实现取决于当前输出；
- 存在需要用户选择的设计取舍；
- 操作具有明显风险或需要额外授权；
- 当前现象需要先解释清楚才能继续。

每次给出工作单元时，应先简要说明为什么现在要做它、它解决什么具体问题，再说明目标、范围、主要操作、验证方法和停止条件。动机说明保持简短，不借此提前展开实现方案。一个工作单元应小于整个里程碑，但大于单个命令或纯机械操作。

职业定位：

项目用于补充协议、路由、模型调用治理和兼容性证据；既有备份、迁移、集群管理、灰度发布和故障处理经历承担生产系统经验的证明。个人项目不能替代真实的 Kubernetes 大规模集群、GPU 调度或推理引擎研发经历。

核心闭环：

~~~text
测试客户端 / curl / 标准 SDK / 可选 Study Assistant
  → Gateway 协议、鉴权、路由和治理
  → Upstream 执行（区分客户端请求与每次上游尝试）
  → 状态、延迟、Usage、错误及必要的 Trace
  → 确定性测试、故障实验和指标
  → 最小改进、复验和求职证据
~~~

AI Gateway 是唯一项目主线。Study Assistant 是可替换、可冻结的验证入口，不设独立产品路线。确定性测试和故障实验承担正确性证明，标准客户端与真实 Provider 承担兼容性补充证明，两者不能相互替代。

目标 JD 可以成为新增验证的需求来源，不要求先制造产品用户。Agent 专项优先使用独立、可冻结的样例；工具执行和任务编排不进入 Gateway 数据面，也不要求继续扩展 Study Assistant。

# 3. 目标系统与演进约束

## 3.1 目标系统

```text
curl / 标准 SDK / 可选参考 CLI
              │ HTTP / SSE
              ▼
           Go Gateway
 Auth / Router / Rate Limit
 Timeout / Retry / Fallback / Circuit
 Logs / Metrics / Token / Cost
              │
       ┌──────┼──────────┐
       ▼      ▼          ▼
    Mock A  Mock B  Real LLM / Local Model
              │
        可选 MySQL / Redis
```

运行方式按需求演进：本地进程 → Docker Compose → 可选 Kubernetes。

## 3.2 参考客户端最小边界

当前 Study Assistant 只实现以下验证能力：

- 发起非流式或 SSE 请求；
- 输出模型结果、Gateway Request ID、必要耗时和错误；
- 能触发 Gateway 当前需要验证的客户端行为，例如流式读取和主动取消；
- 只知道 Gateway 地址、客户端 Key 和逻辑模型；
- 不知道真实上游地址与 Provider 密钥。

不要求保存历史、评价模型答案、自动修改仓库，也不扩展为完整聊天产品、Agent、向量数据库或复杂 RAG。

Study Assistant 达到“能发起当前 Gateway 调用、观察结果和触发必要的客户端行为”后即停止扩展并允许长期冻结；协议兼容、超时、取消、失败、Token、成本和指标的实现与主要证据应落在 Gateway。Mock 只提供确定性验证所需的最小上游行为，优先由局部测试服务器承担；只有手动演示或 Compose 复现需要时才增加常驻 Mock 能力。任何里程碑都不能仅因缺少 Study Assistant 新功能而阻塞。

## 3.3 架构原则

- 为同一逻辑模型的多上游选择与 Fallback 验证扩展 Router；可由确定性 Mock 证明行为，不等待第二个真实 Provider；
- 长响应需要改善体验时引入 SSE；
- 用两个可区分的调用方验证 Auth、并发隔离和配额，不等待实际产品用户；
- 可复现上游故障后引入 Retry、Fallback 和熔断；
- 服务数量增加后引入 Compose；
- 多副本出现后再引入 Redis；
- 只有目标岗位或实际管理需求明确时才做持久化 / Admin API；React 单独判断，不与后端证明绑定。

只有满足以下至少一项时才新增抽象：

- 已有两个真实实现；
- 测试需要替换依赖；
- 当前模块职责已混杂；
- 明确的后续需求能通过抽象降低复杂度。

## 3.4 配置与模型注册的唯一事实来源

Route、Upstream 和模型注册使用同一份领域语义演进：

1. P0 默认由 YAML / JSON 在启动时生成不可变运行快照；
2. 未做数据库时，模型能力、价格和路由规则继续扩展同一份文件结构；
3. 若后续引入数据库，文件只负责首次导入，Admin API 修改数据库并原子替换运行快照；
4. 不允许文件和数据库同时静默覆盖配置，也不建立平行的注册模型；
5. 请求记录保存实际快照标识、逻辑模型、Provider 和路由结果，避免配置变化改写历史语义。

# 6. 阶段 B：工程核心（W4～W7）

完成本节还需第 7 节 W10-M1 和 W11-M1，才达到 v7 的检查点 B。远期验收规定结果，不预先指定实现结构。

## 6.1 W4：鉴权与调用方隔离

目标：调用方身份、请求频率与长连接占用都可控制。

核心范围：

- Bearer API Key；客户端 Key 与 Provider Key 分离，不进入日志、镜像或 Git；
- Request ID、Logging、Auth 的职责和顺序明确，调用方只能访问授权的逻辑模型；
- 单进程总并发上限与最小按 Key 并发上限，明确它们不等于跨副本全局上限；
- 内存版按 Key RPM 限流，稳定返回 401 / 429 及适用的重试提示；
- 正常调用、故障实验和压测使用不同 Key；只实现一种限流算法并解释边界。

验收：

- 鉴权失败、越权模型访问、脱敏、窗口恢复和调用方独立计数有测试；
- 流式并发名额持续到请求终止，不在收到响应头时提前释放；
- 成功、失败、取消均恰好释放名额；同一请求的重试不重复占用调用方请求名额；
- 长连接调用方受到自身上限约束，为其他调用方保留可用容量；明确这不等于完整公平调度；
- 并发测试与 Race Detector 通过，无名额或 Goroutine 持续泄漏。

## 6.2 W5：多上游选择与稳定性组合治理

目标：请求、内部上游尝试和失败切换形成统一、有限、可解释的生命周期。

W3-M2 负责流式基础生命周期；本主题在其上增加治理，不重复基础 SSE 实现。

职责边界：W4 判断调用方能否访问逻辑模型；W5 只在该逻辑模型的内部候选集中选择 Upstream。候选资格由配置、能力、健康 / 熔断状态和切换策略决定，Provider 凭证是 Gateway 的执行条件，不向调用方暴露，也不建立调用方到具体 Provider 的授权关系。

核心范围：

- 区分连接、响应头、整体和流空闲超时；普通请求与流式请求策略不同；
- 同一逻辑模型配置至少两个合格候选上游，校验配置完整性、最小能力、当前可用性与切换许可；
- 对合格候选实现一种简单负载分配策略，例如轮询；无须复杂动态权重；
- 明确“逻辑模型映射”“正常负载分配”“失败后的 Fallback”是不同职责；
- Retry 与 Fallback 共享最大尝试次数及发送前时间预算；退避、等待和尝试都受取消与剩余预算约束；
- 响应未开始只是可考虑重试的必要条件：结合请求可重放性和失败类型决定是否允许，不承诺上游未执行或未计费；
- 响应开始后不 Retry、不 Fallback，不拼接另一模型的结果；流式传输使用独立生命周期策略；
- 线程安全、可确定性测试的简化熔断器；区分调用方取消、本地限流、鉴权与 Provider 故障；
- 每次上游尝试有结果记录，供 W6 观测和 W10 Usage 聚合复用。

验收：

- 受控重复请求证明同一逻辑模型可分配到不同上游，路由和切换原因可追踪；
- 不合格、不可用或不具备切换许可的候选不会被 Fallback 选中；无可用候选返回可解释失败；
- Retry 与 Fallback 组合不放大尝试上限；客户端取消后不再开始新的尝试；
- 用户取消、本地限流不直接计入 Provider 熔断失败；其他状态有明确分类策略；
- 连接失败、慢响应、上游错误、限流、断流、慢客户端、全部候选失败可重复验证；
- 在限流、取消、重试、熔断组合下验证名额、连接、内存和 Goroutine 回收；
- 沿用或新增一个真实发现的问题，保留“复现 → 最小修改 → 同条件复验”证据供 W11 使用。

## 6.3 W6：可观测性与性能（可选最小 Trace）

目标：能够用数据解释客户端请求与多次上游尝试，而不是只证明安装了观测组件。

P0 核心范围：

- 请求量、错误、并发、延迟、每次上游尝试、Retry、Fallback、熔断和限流指标；
- 流持续时间、中断与取消；区分客户端最终结果和上游尝试结果；
- 写清响应头等待、首字节、首个 SSE 事件、首段有效输出各自的起止点；未解析有效输出时不得把首字节指标直接称为 TTFT；
- Label 控制基数，不使用 Request ID、原始 API Key 或 Prompt；
- 可从仓库恢复的 Grafana Dashboard；受保护的 pprof 入口；
- 固定环境、版本、并发、负载、命令与指标口径的 Benchmark。

性能证据分开记录：受控 Mock 用于观察 Gateway 开销、资源行为与故障；真实模型用于兼容性和端到端体验。不得把模型生成耗时写成网关自身开销，不预设优化幅度，不要求制造问题。没有异常时完成受控 pprof 采集并如实解释结论。

P0 验收：指标可抓取且与故障对应；Dashboard 可恢复；实验可复现；能解释至少一个瓶颈、边界或无明显异常的结论。

### 最小 OpenTelemetry 专项（P1；明确要求该能力的岗位前置）

范围：一条 Gateway 入站轨迹与每次上游尝试的子操作；关联 Trace 和日志；通过一个可视化入口查看成功、失败及 Fallback。不要求自建可观测平台或在所有函数上埋点。

验收：

- 能看到“请求 → 尝试 1 失败 → 尝试 2 完成”的关系、耗时和结果；
- 流式轨迹反映实际结束 / 取消，不能在发出响应头时提前结束；
- 有必要的上下文传播及脱敏策略，不记录完整 Key、Prompt 或工具敏感参数；
- Trace 导出异常不改变正常调用语义，缓冲与资源使用有界；
- 明确该项是否完成；未完成不声称具有 OpenTelemetry 实践。

## 6.4 W7：容器、测试、CI 与交付环境

核心范围：

- 多阶段镜像、非 root 运行，镜像 Tag 可关联 Git Commit；
- Compose 启动 Gateway、验证 Upstream、Prometheus 和 Grafana；Study Assistant 可选；

- 在干净环境运行 5～10 分钟 Demo。

验收：新环境按 README 可启动；本地与 CI 语义一致；停止后可重启；无真实密钥泄露；核心行为不依赖外部 Provider；真实 Provider 版本与兼容性验证状态明确。

本主题只验收交付环境。完成 W10-M1、W11-M1 并核对第 9.4 节后，才关闭检查点 B。

- Kind、Minikube 或 K3d 任选一种；理解 Deployment、Service、ConfigMap、Secret、资源 requests / limits 和探针；
- 至少两个 Gateway 副本，用受控实验观察内存限流偏差与 Redis 原子共享限流；
- 明确计数键、窗口、过期、原子性和 Redis 故障时 Fail-open / Fail-closed 的选择；
- 区分全局 RPM 配额与跨副本并发限制；只实现前者时必须明确后者仍是本地限制；
- 演示滚动发布、版本回滚、停止接流、在途请求排空与有界终止；
- 验证发布过程中的 SSE 结束、取消或超预算中断，不宣称无限长流零中断；
- 重新评估当前依赖 Upstream 的 readiness：明确 Gateway 自身就绪、上游可用性与流量入口的关系；
- HPA、Operator、自定义调度器和 GPU 组件不进入该专项默认范围。

验收：Pod 重建后恢复；共享配额可重复验证；Redis 故障行为可解释；普通上游故障不造成重启风暴；发布时探针、接流、SSE 与退出顺序有实验记录；回滚结果可观察。记录本地集群规模和限制，不包装为生产集群经验。

如果 JD 硬性要求 Kubernetes 二次开发，应单独评估 client-go / Controller / CRD 等深度专项及经验差距，不能凭以上验收直接判定满足。

## 8.3 开源贡献（原 W12，P1）

选择一个与当前项目问题相关、范围清楚的 Issue：复现 → 阅读调用链和测试 → 给出证据 → 聚焦补丁 → 执行项目验证 → 条件允许时提交并回应反馈。

源码阅读、已提交 PR、已合入贡献分开记录。外部维护者决定不阻塞项目或投递，不以 PR 数量作为验收。

## 8.4 Agent 调用与任务生命周期（Agent 岗位专项）

### 最小工具调用样例

目标：证明理解 Agent 与模型网关的边界，不建设完整 Agent 产品。

- 独立、可冻结的客户端样例经过 Gateway 完成“模型请求工具 → 客户端执行 → 工具结果回传 → 最终回答”；
- 工具限于受控只读能力，有参数校验、超时、取消和最大步骤数；不执行不可信任意代码；
- 验证必要请求字段、工具调用标识和流式增量不被 Gateway 破坏；更新兼容矩阵；
- Gateway 只负责模型调用治理，工具执行、循环和状态位于客户端 / Agent 层；
- 用确定性上游证明成功、工具失败、取消及达到步骤上限的终止行为；真实模型只作兼容性补充。

验收：完整链路可复现，失败可解释，取消不继续启动工具或下一次模型调用，无无限循环。样例不称为完整 Harness、MCP 平台或评测平台；若 JD 明确要求 MCP，另补一个标准客户端与受控服务器的调用验证，不把一般工具调用等同于 MCP。

### 任务编排增量（仅具体 JD 要求时）

最小范围：任务提交与查询、状态机、幂等、有限重试、取消、并发上限和持久化恢复。复用既有存储 / 控制面经验，先解决任务生命周期，不搭完整评测系统或引入不必要的 MQ。

验收：重复提交不重复创建逻辑任务；服务重启后可恢复未完成任务；终态不会被迟到结果覆盖；说明至少一次执行与重复副作用边界，不承诺任意外部工具 exactly-once。沙盒隔离、奖励模型、多智能体和完整 Harness 另立长期专项。

## 8.5 特定网关、协议与其他专项

- Bifrost / LiteLLM / Higress / Envoy / APISIX / Kong：按目标岗位选一个，深入一条与自身项目相关的协议、路由、流式或治理调用链，形成带版本和证据的对照记录；不同时研究全部项目；
- Responses、异构 Provider 原生协议、结构化输出或多模态：由具体 JD 或应用验证触发；最小 Tools 支持按第 8.4 节，不再笼统放到远期；
- HPA：先有可靠指标与资源配置，再验证，不作为全部平台岗门槛；
- 前端和视觉优化：仅由明确的 B/S 或全栈岗位需求触发。

## 8.6 与项目并行的面试与工作经历准备

这些准备不绑定 MySQL 管理页面，也不要求全部写进 Gateway。

- Go：并发、Context、资源生命周期、内存与性能分析；结合代码解释，不只背术语；
- 基础：网络、HTTP / RPC、Linux、常用数据结构与算法、系统设计；
- SQL：索引、事务、并发更新、幂等；Redis：原子性、过期、一致性与故障；异步任务：重复消费、重试、背压与恢复；
- 必要时用用量记录或任务元数据做一个小型持久化实验，不为此强行开发完整 CRUD 平台；
- 准备至少三个真实工作案例：备份链路改造；迁移 / 缩容 / 清理的风险与回滚；一次线上故障定位与防复发；
- 每个案例说明背景、约束、本人职责、方案取舍、验证、结果和边界；没有可核实数字时不补造收益；
- 准备待业期、转型理由、英文项目介绍和技术沟通；面试反馈进入 W11-M2。

可用标准：能脱离项目 README 解释关键原理；能将生产经历与 Gateway 能力迁移关联；简历不把个人实验写成 58 同城的生产成果。此项持续推进，不设“所有知识学完”才投递的门槛。

# 9. 完成标准与交付检查点

## 9.1 一次学习时段可以结束

- 完成一个可运行或可验证的完整工作单元；
- 用户能解释至少一个核心概念；

- 明确下一步从哪里继续。

普通学习时段不强制全量测试、正式文档或 Git 提交。

## 9.2 代码类里程碑完成标准

- 功能或实验已存在于仓库；
- 有端到端演示或可复现验证步骤；
- 有与风险相称的自动化测试；
- 当前里程碑验收项全部通过；
- 行为、协议或重要设计变化已更新文档；
- `go test ./...` 通过；
- 涉及并发时 `go test -race ./...` 通过；
- 没有用临时硬编码绕开核心学习目标；
- 形成至少一个边界清晰、可回退的提交；
- 当前实现、简化项和后续演进可以解释。

## 9.3 文档、调研或求职类里程碑完成标准

- 目标产物存在且范围清楚；
- 结论可以追溯到代码、测试、指标、公开资料或真实记录；
- 不使用无法验证的性能或生产级表述；
- 若涉及代码，只运行与实际改动相称的验证；
- 外部条件未满足时记录限制，不伪造完成状态。

## 9.4 三道交付检查点与按岗证据

本节只定义检查点验收条件，不单独维护完成状态；当前阶段、里程碑和检查点状态统一以第 1.1 节为准。

### 检查点 A：最小可验证 AI Gateway

- 测试客户端、curl 或标准客户端只通过 Gateway 调用；
- 至少两个可区分的验证用 Upstream、逻辑模型路由和配置校验可用；
- 非流式和 SSE 调用面稳定；
- 流式输出、取消和失败边界可重复验证；
- Request ID、结构化日志、Health 和 Ready 可用；
- 核心证据来自确定性测试；真实 Provider 兼容性状态已验证或明确记录。

### 检查点 B：可投递 AI Gateway / LLM 后端核心版

依赖：A + W4～W7 + W10-M1 + W11-M1。以下项目均须在 B 前形成可追溯证据，不能因版本更新自动视为完成。

- Auth、模型访问边界、按 Key RPM / 并发和单进程总并发可用；
- SSE 名额保持至终止，组合故障下资源正确释放；
- Retry / Fallback 共享有限预算，已开始响应不切换，熔断分类明确；
- 同一逻辑模型多上游负载分配、合格候选筛选和路由原因可验证；
- 一个标准客户端的非流式 / 流式调用、兼容矩阵与真实 Provider 证据可追溯；
- Usage 覆盖非流式、流式、取消、缺失和多次尝试，unknown 不当成零；
- Prometheus、Dashboard、Benchmark 与 pprof 证据可复现，指标口径明确；
- Compose 可启动，CI 通过，停止与在途请求的有界生命周期明确；
- 至少一个工程问题完成证据闭环；README、架构、Demo、至少 3 条简历描述和面试材料可使用；
- 已知限制与生产经验边界明确，核心验证不依赖外部 Provider。

通过后启动主线投递。最小 Trace、Kubernetes、Agent、管理面与 C 不自动成为本检查点附加条件。

### 检查点 C：投递后完整作品增强

- B 已完成，W10-M2 / W11-M2 的增量有证据；
- 模型版本、配置 / 价格快照及用量状态可追溯，估算成本不冒充账单；
- 受控请求的路由、延迟、Token 与估算成本比较可复现；
- 求职材料反映新增能力、实际岗位反馈和仍未满足的硬门槛。

### 按岗证据清单（独立选择，不要求全部完成）

- 云原生 / 平台岗：第 8.2 节多副本、Redis、探针、发布、SSE 排空与回滚实验；
- Agent 后端岗：第 8.4 节工具调用闭环、失败、取消和步骤上限；
- 任务平台岗：按具体 JD 选择任务幂等、状态机、重试和持久化恢复增量；
- OpenTelemetry 明确要求岗：第 6.3 节一次请求与多次上游尝试的轨迹；
- 特定网关岗：第 8.5 节一个项目的源码对照、复现或真实贡献。

每项记录“适用 JD、已完成证据、未覆盖要求”；未选择的专项注明不适用，不伪装成已完成。硬性生产年限、Kubernetes 二次开发和 GPU 调度经验另行判断。
