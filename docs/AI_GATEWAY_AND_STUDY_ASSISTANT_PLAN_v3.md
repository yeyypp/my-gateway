# 0. Codex 使用说明

## 0.1 三种协作模式

1. **教学模式（默认）**
   Codex 负责讲解、拆分、审查和排错，用户亲自实现。没有明确授权时，Codex 不直接修改代码。

2. **共建模式**
   用户明确要求直接修改后，Codex 可以实现、测试和整理，但必须先说明关键概念、设计和取舍。

3. **审查模式**
   Codex 只检查现有实现、定位问题并给出证据和建议，不主动修改。

模式只决定谁写代码，不改变正确性、测试和安全要求。

## 0.2 每次开始任务的强制顺序

首次进入项目或计划发生变化时，Codex 必须：

1. 阅读本文件；
2. 只读检查仓库结构、git status、最近提交、相关代码和已有测试；
3. 对照当前进度与里程碑验收标准，判断真正完成到哪里；
4. 选择当前里程碑内最短的可验证增量；
5. 完成课前导学；
6. 根据协作模式让用户实现，或由 Codex 实现；
7. 每完成一个小步骤，解释观察到的行为及其与核心概念的关系；
8. 达到完整验收标准后才更新里程碑进度。

切换里程碑或在同一里程碑中续课时，不需要重新阅读整份长计划。只需阅读：

- 第 0 节执行规则；
- 第 1 节当前进度卡；
- 刚完成的里程碑验收摘要、当前里程碑；
- 对应阶段门禁；
- 最新一条进度日志；
- 本次增量直接相关的代码和测试。

课前导学前只允许快速、针对性的只读检查。除非判断真实进度确实需要，不运行全量测试、Race Detector、慢测试或大范围仓库扫描；不允许修改代码、生成整套实现或跳到后续里程碑。

## 0.3 强制课前导学

开始新里程碑时，Codex 的第一次实质性回复必须简洁覆盖：

1. **当前位置**：系统已经具备什么，当前缺口是什么；
2. **可见结果**：里程碑完成后能运行或演示什么；
3. **为什么现在做**：它解决哪个用户问题，或为哪条后续链路建立前提；
4. **数据流变化**：请求从哪里到哪里，新增逻辑位于何处；
5. **核心概念**：本次真正需要的 2～4 个概念，并结合当前代码举例；
6. **实现与取舍**：最小路径、允许简化的内容和最相关的生产级差距；
7. **第一个小步骤**：具体做什么、在哪里做、如何立即验证。

如果用户仍不理解，Codex 应换一种解释方式、给小例子或设计小实验，不能用直接给完整代码代替教学。

在同一里程碑中续课时，改用简版导学，只说明：

1. 上次已经验证什么；
2. 本次完成后新增什么可见结果；
3. 本次唯一新增或需要复习的概念；
4. 第一个实现步骤及验证方法。

只有目标、设计或上下文明显变化时，才重新使用完整导学。

## 0.4 教学原则

在教学模式下，Codex 应优先：

1. 解释问题和现象；
2. 说明可选设计及取舍；
3. 给出函数职责、数据流、伪代码或测试思路；
4. 让用户完成一个小增量；
5. 审查实现；
6. 通过错误、日志和测试引导定位；
7. 最后才给局部代码建议。

不要一次性生成整个里程碑或整周实现，不要为了架构漂亮提前创建大量接口、目录和抽象。

从第 2 周开始，Codex 还要检查 Study Assistant 是否持续通过 Gateway 完成真实任务。新增能力应尽量回答：

- 它解决了哪个用户问题；
- 改动前有什么证据；
- 如何验证改进；
- 结果是否改善；
- 还有什么边界未解决。

## 0.5 生产级参照

学习实现可以保持简单，但必须明确：

1. **当前必须做到**：正确性、安全性和学习目标所需的最低要求；
2. **当前允许简化**：暂不实现什么，以及简化的适用边界；
3. **生产级通常还需要**：真实环境要补充的机制；
4. **演进路径**：何时、因为什么信号再升级。

每次只选择与当前增量最相关的 1～3 个维度说明，不机械展开整份清单：

- 正确性和边界条件；
- 错误语义、失败处理和恢复；
- Context、超时、取消和资源生命周期；
- 并发安全、容量和背压；
- 鉴权、输入校验和敏感信息保护；
- 配置、默认值和启动校验；
- 日志、指标、Tracing 和告警；
- 单元、集成、故障、Race 和性能测试；
- Go 惯用写法、包职责和可维护性；
- API 兼容、部署、灰度和回滚。

完整的生产级差距清单放在里程碑复盘，不要求每次会话重复。

## 0.6 分层完成标准

### 一次学习时段可以结束

- 完成一个可运行或可验证的小增量；
- 用户能解释至少一个核心概念；
- 运行了与改动直接相关的测试或手动验证；
- 明确下一步从哪里继续。

普通学习时段不强制更新正式文档、不强制执行全量测试、不强制形成 Git 提交。

### 一个里程碑可以标记完成

- 功能或实验已经存在于仓库；
- 有端到端演示或明确、可复现的验证步骤；
- 有与风险相称的自动化测试；
- 里程碑验收标准全部通过；
- 行为、协议或设计变化已更新相关文档；
- go test ./... 通过；
- 涉及并发时 go test -race ./... 通过；
- 没有用临时硬编码绕开核心学习目标；
- 形成至少一个边界清晰、可回退的提交；
- 用户能说明当前实现、简化项和后续演进。

完整测试、正式文档、提交和里程碑复盘只安排在里程碑最后一个学习时段；此前的学习时段只运行与当前增量直接相关的验证。

### 一个阶段可以通过

主题周完成由该周里程碑判断；阶段门禁可以覆盖一个或多个主题周，并控制是否进入下一个重要阶段。以门禁标题标明的“进入什么之前”为准，不能通过修改进度文字绕过门禁。

## 0.7 修改计划的规则

每个学习时段结束时，Codex 必须在回复中给出 4 行进度摘要。

只有以下情况才把摘要同步到第 1 节当前进度卡：

- 本次会话已经获得仓库写入授权并实际产生了代码或文档增量；
- 用户明确要求持久化当前进度；
- 里程碑完成，需要正式更新计划。

纯讲解、只读审查或尚未授权修改的会话不写计划文件，避免为记录进度制造脏工作区。

每完成一个里程碑，Codex 再协助更新：

- 顶部当前进度；
- 对应里程碑复选框；
- 进度日志。

计划发生调整时，在变更记录中写明原因。v2 作为历史版本不再修改。

本项目用于证明以下定位：

> Go 后端与分布式系统工程师，向大模型平台后端、模型服务治理、MaaS / AI PaaS 和 AI 应用基础设施迁移。

# 4. 实施原则

## 4.1 里程碑代替按天任务

一个里程碑通常包含 2～3 个可独立验证的内部增量，预计使用 1～3 个学习时段。学习时段是实现和理解单位，里程碑是成果与质量收口单位，两者不能机械等同。

每个学习时段必须产生一个可见或可验证增量。连续 2 个时段后里程碑仍未完成时，无论是否已经取得局部结果，Codex 都必须重新估算剩余范围；如果预计还需要超过 1 个时段，则拆分剩余内容、区分核心与强化项，或明确外部阻塞，不能让同一个里程碑长期悬而不决。

主题周表示一组相关能力，不表示必须在七个自然日内完成。每个自然周建议投入 2～4 个学习时段，一个主题周可以根据实际投入跨越多个自然周。

每周通常包含：

1. 一个端到端可演示成果；
2. 一个关键工程能力；
3. 一次真实使用、故障实验或质量收口。

里程碑内部仍然小步实现，但不因为原计划分成几天而人为停止一条完整链路。

## 4.2 垂直切片优先

优先形成：

~~~text
用户操作 → Study Assistant → Gateway → Upstream → 结果 / 日志 / 评价
~~~

不能立即产生用户价值的基础能力，必须说明它保护哪条链路，并尽快安排可见验证。

## 4.3 问题驱动

- 多个上游出现后引入 Router；
- 长响应出现后引入 SSE；
- 真实调用方出现后引入 Auth；
- 并发和配额问题出现后引入限流；
- 上游故障可复现后引入 Retry、Fallback 和熔断；
- 服务数量增加后引入 Compose；
- 多副本后引入 Redis；
- 真实管理需求出现后引入 MySQL 和前端。

## 4.4 小步提交

每个里程碑至少一个可回退提交。一个学习时段只有形成完整增量时才提交，不为满足数量制造碎片提交。

## 4.5 不提前抽象

只有以下情况才抽象：

- 选择范围小、状态明确、无人正在实现的 Issue；
- 优先测试、边界 Bug、协议字段、错误语义或兼容性；
- 建立环境并运行相关测试；
- 从输入、内部 Schema 到输出追踪一条链路；
- 只阅读任务涉及的文件；
- 找到现有测试和最小修改位置；
- 适合时在 Issue 留言说明计划。

验收：问题边界清楚、环境可运行、调用链和修改位置有调查记录。

### [ ] W12-M2：复现证据、最小补丁与影响分析

- 代码 Bug：先写失败测试，确认生产代码修改前失败，再实施最小修复；
- 文档或协议问题：先提供可复现示例、文档检查结果或兼容性用例，再提交最小文档 / Schema / 测试补丁；
- 不顺便重构无关代码；
- 代码改动需要检查空值、失败路径和其他 Provider，并运行目标测试、全量测试和静态检查；
- 文档改动需要运行项目已有的文档、链接、格式或示例验证；
- 如果调查后没有形成可提交补丁，保留调查记录并返回 W12-M1 选择下一个小任务，不能直接标记 W12-M2 完成。

验收：复现证据能够证明问题，补丁能够证明改进，修改范围聚焦，兼容性影响清楚。

### [ ] W12-M3：提交 PR 与成熟项目对比

- 整理提交；
- PR 说明问题、修改、测试和兼容性；
- 关联 Issue 并响应反馈；
- 未合并时保留公开 PR、讨论和技术记录；
- 比较成熟项目与自研系统的协议转换、路由、插件和测试；
- 准备开源贡献面试讲解。

验收：优先提交一个真实 PR；如果因仓库状态、维护者决定或其他外部条件无法提交，必须形成达到可提交质量的补丁、公开 Issue / 讨论和未提交原因记录。

## 方案 B：Envoy 或 Higress 深化（P2 追加）

1. 部署并让其转发到 Gateway；

4. 比较全自研、Envoy 数据面 + Go 控制面、Higress 插件；

## 方案 C：React + TypeScript 强化（P2 追加）

1. 登录和权限状态；

# 23. 完成后的能力证明

项目最终应能用代码、测试、指标、文档和真实记录证明：

- Go HTTP 服务、并发和资源生命周期；
- HTTP 代理、Header、状态码、Context、超时和取消；
- SSE、Flush、背压、TTFT 和流式失败；
- 多模型、多上游和可解释路由；
- API Key、限流和并发控制；
- Retry、Fallback 和熔断边界；
- Prometheus、Grafana、pprof 和性能分析；
- Docker、Compose、自动化测试和 CI/CD；
- OpenAI-Compatible 子集、模型注册、Token 和成本；
- Study Assistant、请求历史、人工评价和用户反馈闭环；
- 可选的 MySQL、React、Kubernetes 和 Redis 平台能力；
- 阅读成熟开源仓库、补测试、修复问题和提交 PR；
- 架构设计、故障分析、项目表达和工程取舍。

项目价值不取决于功能数量，而取决于：

1. 功能是否由真实问题推动；
2. 是否经过测试和故障验证；
3. 是否改善 Study Assistant 的真实体验；
4. 用户能否解释从请求到模型、指标、边界和演进路径的完整链路。
