## 0. Codex 使用说明

### 0.1 每次开始任务前

Codex 应先完成以下步骤：

1. 阅读本文件；
2. 检查当前仓库结构、`git status`、最近提交和测试结果；
3. 对照“当前进度”与每一天的验收标准，判断真正完成到哪一步；
4. 只处理当前未完成的一天，不提前堆叠后续功能；
5. 先说明当天要解决的问题、相关概念、最小实现路径及对应的生产级参照，再辅助用户实现。

### 0.2 教学原则

本项目以用户亲自实现为主。除非用户明确要求直接修改代码，否则 Codex 应优先：

1. 解释当前问题；
2. 指出可选设计及取舍；
3. 给出函数职责、数据流、伪代码或测试思路；
4. 让用户先写；
5. 审查用户实现；
6. 通过错误现象、日志和测试引导用户定位；
7. 最后才给出局部代码建议。

不要一次性生成整天甚至整周的完整实现，不要为了“架构漂亮”提前创建大量接口、目录和抽象。

#### 0.2.1 以生产级实践作为教学参照

本项目允许学习阶段的实现保持简单，但教学、设计和代码审查应尽量以生产级代码为目标和参照。这里的“生产级”不是要求用户从第一天起实现所有复杂机制，而是要求 Codex 说明一个功能在真实生产环境中的完整形态、质量要求和风险边界。

每次指导实现或审查代码时，Codex 应明确区分：

1. **当前必须做到**：为了保证正确性、安全性和当天学习目标，当前实现不可省略的内容；
2. **当前允许简化**：为了控制学习范围而暂不实现的内容，以及这样简化的适用边界；
3. **生产级通常还需要**：真实生产环境中需要补充的设计、异常处理、测试、可观测性和运维能力；
4. **演进路径**：从当前实现升级到生产实现的合理时机和步骤。

生产级参照不能只停留在“还要优化”这类笼统描述。应结合当前功能，具体说明以下相关维度：

- 正确性与边界条件；
- 错误语义、失败处理和恢复策略；
- Context、超时、取消以及连接、Body、Goroutine 等资源生命周期；
- 并发安全、容量上限和背压；
- 输入校验、鉴权、敏感信息保护等安全要求；
- 配置管理、默认值、启动校验和动态变更边界；
- 结构化日志、指标、Tracing 和告警；
- 单元测试、集成测试、故障测试、Race Detector 和必要的性能测试；
- Go 惯用写法、命名与注释、错误包装、依赖管理、`gofmt`、`go vet` 和适用的静态检查；
- API 兼容性、代码可读性、包与模块职责和可维护性；
- 部署、灰度、回滚和运行手册等运维要求。

Codex 在给出生产级参照时，应提供与当前任务相称的具体示例，例如关键接口或数据结构、局部代码、测试用例、失败场景或检查清单；不要求一次性给出完整生产系统。

“当前不实现”不等于“不需要了解”。凡是为了学习节奏而省略的生产级能力，应说明省略原因、可能风险和后续补齐位置。反过来，也不要仅以“生产级”为理由提前引入尚无真实需求的框架、中间件或抽象。

### 0.3 进度判断规则

某一天只有在以下条件都满足时才能标记完成：

- 功能已经存在于仓库；
- 有相应测试，或有明确且可复现的手动验证步骤；
- 验收标准全部通过；
- 当天要求的文档已经补充；
- `go test ./...` 通过；
- 涉及并发时，`go test -race ./...` 通过；
- 没有用临时硬编码绕开当天要学习的核心问题。

Codex 不应仅根据“我做完了”直接更新进度，应结合代码和验证结果判断。

### 0.4 修改本文件的规则

每完成一天，Codex 可以协助更新：

- 顶部“当前进度”；
- 对应日期前的复选框；
- “进度日志”。

不要删除原计划。计划需要调整时，应在“计划变更记录”中写明原因。

# 2. 项目最终目标

实现一个可用于求职展示的 AI Gateway，具备以下能力：

1. 使用 Go 实现高并发 HTTP 网关；
2. 支持多个模型和多个上游；
3. 支持普通响应与 SSE 流式响应；
4. 支持 API Key 鉴权、并发限制和请求限流；
5. 支持超时、有限重试、Fallback、健康检查和简化熔断；
6. 提供结构化日志、Prometheus 指标、Grafana 看板和性能报告；
7. 使用 Docker Compose 一键运行完整开发环境；
8. 通过 GitHub Actions 完成测试、静态检查、构建和镜像构建；
9. 提供 Go Admin API、MySQL 持久化以及 React + TypeScript 管理页面；
10. 部署到 Kubernetes，支持多副本、探针、配置、Secret 和 HPA；
11. 使用 Redis 实现多实例共享的限流状态；
12. 提供 OpenAI-Compatible API，接入至少一个真实或本地模型服务；
13. 形成完善的架构文档、故障分析、压测结果和面试讲解材料；
14. 选做 Envoy 或 Higress 集成，理解控制面与数据面。

# 5. 项目实施原则

## 5.1 问题驱动

每项技术都必须由一个真实问题引入：

- 多个上游出现后再引入 Router；
- 长响应出现后再引入 SSE；
- 并发增长后再引入限流；
- 多副本部署后再引入 Redis 分布式限流；
- 服务数量增加后再引入 Docker Compose；
- 部署和协作需要稳定流程后再引入 CI/CD；
- 管理配置有实际需求后再加入 MySQL、React 和 TypeScript；
- 运行环境复杂后再进入 Kubernetes。

## 5.2 小步提交

每天至少形成一个可回退的提交。提交信息建议：

```text
feat(proxy): propagate upstream status code
test(proxy): cover unavailable upstream
docs(streaming): explain cancellation flow
```

## 5.3 不提前抽象

只有以下情况才抽象接口：

- 已经存在两个真实实现；
- 测试确实需要替换依赖；
- 当前模块职责已经混杂；
- 后续需求已明确，并且抽象能减少而不是增加复杂度。

## 5.4 每日完成标准

每天结束前完成：

- [ ] 功能或实验达到当天目标

# 8. 第 1 周：HTTP 请求生命周期

## 本周目标

从“能转发”提升为“正确理解并处理一次 HTTP 代理请求”。

---

## [x] 第 1 天：梳理现有请求链路

### 实现目标

- 保持当前固定上游转发功能；
- 明确 Gateway 在一条请求中同时扮演 HTTP Server 和 HTTP Client；
- 画出请求和响应经过的代码位置。

### 具体任务

1. 整理当前代码，让程序能够稳定启动；
2. 确认 Gateway 监听端口和 Mock Server 地址；
3. 找出以下步骤对应的代码：
   - 接收客户端请求；
   - 读取或转发请求体；
   - 构造上游请求；
   - 发送上游请求；
   - 接收上游响应；
   - 写回客户端响应；
4. 创建 `docs/request-flow.md`；
5. 画出 Downstream、Gateway、Upstream 的请求和响应方向；
6. 记录当前实现是否会完整读取请求体和响应体。

### 需要理解

- Downstream 与 Upstream；
- HTTP Server 与 HTTP Client；
- 两段独立 HTTP 连接；
- Handler 的职责；
- 反向代理的基本含义。

### 验收标准

- 能通过一次请求得到正确响应；
- 能不看代码口述完整请求链路；
- `docs/request-flow.md` 不超过两页，但包含完整时序；
- 当前代码中不存在明显重复启动或资源泄漏。

---

## [x] 第 2 天：状态码与基础错误语义

### 实现目标

让 Gateway 正确区分客户端错误、上游业务错误和代理错误。

### 具体任务

1. Mock Server 支持：
   - 正常返回 200；
   - 特殊输入返回 400；
   - 特殊输入返回 500；
2. Gateway 正确传递上游状态码；
3. 非法 JSON 返回 400；
4. 上游无法连接时返回 502；
5. 错误响应使用统一 JSON 结构；
6. 日志记录最终状态码和错误类别。

### 需要理解

- 400、500、502 的责任边界；
- 上游返回错误与代理失败的区别；
- 为什么不能把所有错误都返回 500。

### 验收标准

- 200、400、500、502 四种场景均可复现；
- Gateway 不把上游 500 改成 200；
- 上游未启动时不会导致 Gateway 崩溃；
- 至少有两个自动化测试覆盖成功和上游不可用。

## [ ] 第 3 天：请求头与响应头

### 实现目标

理解代理过程中 Header 的传播、重写和过滤。

### 具体任务

1. 打印并比较：
   - 客户端发给 Gateway 的 Header；
   - Gateway 发给 Upstream 的 Header；
2. 正确处理：
   - `Content-Type`；
   - `Authorization`；
   - `Host`；
   - `User-Agent`；
3. 保留必要响应头；
4. 研究 Hop-by-hop Header；
5. 不记录完整 Authorization 值；
6. 在文档中记录哪些 Header 应透传、重写或删除。

### 需要理解

- End-to-end Header；
- Hop-by-hop Header；
- Host 与目标地址；
- 敏感信息日志脱敏。

### 验收标准

- JSON 请求和响应的 `Content-Type` 正确；
- 日志中不出现完整密钥；
- 能解释为什么 `Connection` 不应无脑透传；
- 有测试验证至少一个请求头和一个响应头。

## [ ] 第 4 天：Context 与超时

### 实现目标

为上游请求设置合理超时，并理解 Context 的传播。

### 具体任务

1. Mock Server 支持可配置延迟；
2. Gateway 为上游请求设置超时；
3. 超时后返回明确错误；
4. 区分请求 Context 与手工创建的 Background Context；
5. 确认 Response Body 总会关闭；
6. 记录超时日志和耗时。

### 需要理解

- `context.Context`；
- Deadline；
- Cancel；
- `http.Client` 生命周期；
- 为什么不应每次请求创建一个全新的 Client。

### 验收标准

- 上游延迟超过阈值时请求按预期结束；
- 没有明显连接或 Body 泄漏；
- 超时测试稳定通过；
- 能解释 Context 为什么要从下游请求传给上游。

---

## [ ] 第 5 天：客户端取消传播

### 实现目标

客户端离开后，Gateway 和 Upstream 不继续浪费资源。

### 具体任务

1. Mock Server 提供一个持续运行的慢请求；
2. 客户端发起请求后主动中断；
3. Gateway 检测下游 Context 取消；
4. 上游请求随之取消；
5. Mock Server 能观察到取消；
6. 日志记录取消事件，而不是笼统记录为服务器错误。

### 需要理解

- 客户端断开；
- Context cancellation；
- 取消传播；
- 大模型推理场景中的资源浪费。

### 验收标准

- 客户端取消后，上游能在合理时间内停止；
- Gateway 不继续等待完整响应；
- 有自动化测试或稳定的手动实验脚本；
- 能解释取消和超时的区别。

# 9. 第 2 周：多上游与路由

## 本周目标

从固定代理演进为能够根据模型选择上游的 Gateway。

---

## [ ] 第 1 天：引入两个 Mock Upstream

### 具体任务

- 启动 Mock A 和 Mock B；
- 响应中标明由哪个 Mock 处理；
- 定义最小 `Upstream` 数据结构；
- 不提前设计复杂接口。

### 验收标准

- 两个服务可独立启动和停止；
- 可通过直连确认响应来源；
- Gateway 暂时仍只使用一个固定上游。

---

## [ ] 第 2 天：基于模型的静态路由

### 具体任务

- 请求增加 `model` 字段；
- `model-a` 转发到 Mock A；
- `model-b` 转发到 Mock B；
- 未知模型返回明确的 400 或 404；
- 日志记录模型和选中的 Upstream。

### 验收标准

- 两种模型稳定进入不同上游；
- 路由判断不散落在多个 Handler 中；
- 有模型路由单元测试。

---

## [ ] 第 3 天：配置文件

### 具体任务

- 将 Upstream 地址和模型映射移入 YAML 或 JSON；
- 启动时加载和校验配置；
- 配置错误时快速失败；
- 不做动态热更新。

### 需要理解

- 代码与配置分离；
- 启动期校验；
- 默认值与必填项。

### 验收标准

- 修改配置即可改变路由；
